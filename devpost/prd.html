Personal AI That Remembers — Product Requirements

A single-user personal AI chat whose defining behavior is that it actually remembers — across sessions, on one device. No accounts, no cloud, pure conversation.

The Core Journey

Scope said "the AI picks up where the last session left off." Now we know the whole path that makes it true — including the two moments it must NOT pretend: no invented past, no lost message.

Features & Behavior — click each to expand

Onboarding & Memory Seeding first use

The AI opens onboarding by asking a few facts about the user, conversationally. Answers become the first long-term memories.

  • After onboarding, the AI can correctly reference a seeded fact in later conversation.
  • Onboarding feels like chat, not a form — no questionnaire UI.
Session Continuity — "let's continue" core loop

In any new session, "let's continue" produces a summary of where the last session left off and a proposed next step.

  • Fresh session after a real prior session → accurate "yesterday we looked at…, today…" without hunting through history.
  • Day one (facts but no sessions) → a clarifying question, never a fabricated recap.
Memory Recall — unified store, keyword retrieval core loop

Past sessions resurface automatically when the conversation touches their subject, from one unified store spanning all sessions.

  • Mentioning a topic from an old session triggers recall of that session's relevant content.
  • Recall crosses session boundaries — no per-chat silos.
Visible vs. Invisible Memory — AI's judgment kernel

The AI decides, moment by moment, whether to show its work. Invisible: seamless answers. Visible: a collapsible thought-signature panel above the answer — which session it pulled from, what it took, why it's relevant now.

  • When shown, the panel names the source session and the recalled content.
  • Panels appear only when the AI judges it matters; routine answers flow without them.
Repetition Guard — retrieval over regeneration demo beat

Requesting something already produced in a past session triggers retrieval: the AI points back to the prior conversation and its content instead of generating a new variant. (The CV you asked for last week — "here it is," not a new one.)

  • Repeating a past request yields a reference to the original, not a fresh regeneration.
History View surface

The hamburger toggles a list of past conversations; tapping one opens that conversation. History and memory read from the same store — two lenses on one truth.

  • Every past session appears in the history list.
  • Opening a history item shows the full conversation.
Voice Input kept, minimal

The mic button captures speech through the device/OS built-in speech-to-text — no custom STT or TTS. Rationale: "some thoughts get lost while typing."

  • Dictated speech lands in the input as editable text before sending.
Failure & Recovery error state

If the model call fails, the user sees an error message with a retry button. The sent message is held in short-term memory until a response arrives — nothing is lost or retyped.

  • Network interrupted → error + retry appears; after retry, the original message is answered without retyping.

States & Boundaries

First use — Get Started → onboarding; no accounts anywhere; single local user, data on device.
Empty memory — the AI asks for clarification rather than inventing continuity.
Model failure — error + retry; pending message survives in short-term memory until answered.
Persistence — all conversations persist in unified long-term memory; short-term covers in-flight session state.
Memory visibility — AI judgment only; no user toggle (ephemeral mode was proposed and cut).
Privacy — one user; nothing leaves the device except model API calls.
Key decisions — no auth (on-device data) · device-STT mic · AI-judged visibility · ephemeral mode cut · pure conversation in v1 · Gemini/Claude look, avoid bulky long responses.
Deferred / non-goals — files & artifacts library (first in line, repetition rationale) · memory dashboard · critique mode · multi-user/cloud sync · custom STT/TTS · mobile · deployment · fine-tuning.

Open questions → 4-spec: storage engine, ORM & framework (learner leans SQLite); keyword-retrieval quality bar; dark vs. light theme. None block this PRD; the first two must be resolved before spec approval.
